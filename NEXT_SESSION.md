Инструмент: `tools/models/repair_stone_beetle.py`. Исходник/резерв: `tools/_tmp/stone028-base/rogozhuk_stone.glb`.
Окружение скрипта: `/home/loq/ai/Hunyuan3D-2/.venv/bin/python` (trimesh/skimage/scipy), Blender CLI5.2LTS для упрощения.

По последнему сообщению агента:
- 90000 геометрических вершин,180000 граней, watertight, Euler0.
- Реальные тоннели между плитами и большая щель шеи/груди закрыты voxelwrap/морфологическим восстановлением.
- Последний маленький тоннель наверху за рогом тоже закрыт, проверен конкретным лучом и4 соседними лучами; финальный нейтральный Blender-кадр не показывал magenta внутри корпуса.
- Это **сообщение агента, ещё не независимая приёмка в Godot**.
- Старые UV перенесены по одному source-face на новый треугольник. Новые запаянные участки выглядят дробно/вытянуто. **Обязателен полноценный UVatlas+bake**, не оставлять current sampling как финальную фактуру.

Root подготовил, но ЕЩЁ НЕ ЗАПУСКАЛ:
1. `tools/blender/bake_creature_atlas.py`: Blender source→target emissionbake, новый SmartUVatlas, выгрузка UV по углам; rig не экспортируется.
2. `tools/models/apply_baked_atlas.py`: сопоставляет raw glTF координаты, переносит UV/встроенныйPNG в существующий GLB через Writer. Удаляет устаревшие normal/occlusion/metallicRoughness maps, которые нельзя читать по новому atlas.
3. `tools/models/compact_glb.py`: удаляет неиспользованные старые буферы/accessors/images. После bake файл может превысить GitHub100MB, поэтому компактизация необходима. Инструмент тоже пока не проверен на результате.

Предполагаемые команды (сначала проверить скрипты):
```
blender -b -t 8 -P tools/blender/bake_creature_atlas.py -- tools/_tmp/stone028-base/rogozhuk_stone.glb assets/creatures_hd/rogozhuk_stone.glb tools/_tmp/stone028-atlas 4096
/home/loq/ai/ComfyUI/.venv/bin/python tools/models/apply_baked_atlas.py assets/creatures_hd/rogozhuk_stone.glb tools/_tmp/stone028-atlas
/home/loq/ai/ComfyUI/.venv/bin/python tools/models/compact_glb.py assets/creatures_hd/rogozhuk_stone.glb
```
Перед bake сделать копию текущего геометрического кандидата! Проверить ray misses/чёрные пятна на bake, качество atlas, совпадение UV→позиции, сохранение скелета/анимаций/нормализации весов. Blender конвертирует glTF(x,y,z)→(x,-z,y), обратно(x,z,-y). Helper выгружает уже обратные координаты.

## 2. Водяной Рогожук: текущий кандидат ещё не принят

`assets/creatures_hd/rogozhuk_tide.glb`, инструмент `tools/models/repair_water_beetle.py` (asset extra `sfery_water_beetle_anatomy=6` на момент остановки). Backup `tools/_tmp/water-beetle027-base/rogozhuk_tide.glb`.

Причина найдена по настоящему rest: исходные задние appendages — U-образные плавательные лопатки, **их концы скульптурно сращены с животом**. Generic rear pivots в0.2.7 попали внутрь U, а не в колени/когти. Просто skin/IK это не чинит.
Агент отклонил расправление старых лопаток: оно рвало поверхность. Теперь индивидуально удалены ложные U-отростки, третья пара собрана из собственной полноценной средней ноги tide с её бронёй/когтями/UV, поставлены отдельные joints. Четыре прежние ноги сохранены.
Последнее сообщение: новые задние ноги выглядят отдельными, стоят на высоте опоры; обычный веерный cap вогнутой раны живота дал звезду и был отклонён. Агент перестроил гладкую закрытую стенку брюшка, добавил сегментные полосы и дошёл до QA. **Финального сообщения об успешной приёмке не было.** На момент остановки скрипт писал anatomy=6. Проверить текущий GLB фактически — не считать готовым по номеру!
Нужны рендеры всех6 лап/rest/idle/appear/attack, отсутствие повторного сращения/дырок/сферических выступов, правильные inverse binds после переноса rear joints, опора всех6 ног. Если внутренний объём опять только прикрывает рану, восстановить саму наружную стенку.
